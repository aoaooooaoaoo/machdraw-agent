## 2. 先给结论：我们不是"同一类物种"

这 12 个项目其实分属四种物种，我们的定位和它们**都不同**：

```
通用 AI 平台          教育大模型            教学引擎/学习系统          检索基础设施
open-webui        EduChat              tutor-mcp                RAGFlow
LobeHub                                Notebook-LM-Mini        LightRAG
AnythingLLM                            Socratic-Edu-System     KAG
                                       LearnHouse（LMS）
                    └────────────── 我们 ──────────────┘
              单门课程 · 确定性计算 · 引用可审计 · 多画布 · 教师端
```

- **通用平台**解决"接模型、传文档、聊天、插件"——不解决"这门课对不对"。
- **教育大模型**解决"教学语气/启发式/情感"——不解决"教材第 7 章第 3 节怎么说的、这个数算得对不对"。
- **教学引擎/学习系统**解决"学习者状态、路径、复习、判分"——大多假设内容由 LLM 生成或学校已有 LMS。
- **检索基础设施**解决"多跳、图谱、引用、多模态"——但都不是面向学生的课程产品。

我们的差异点可以压成一句话：

> **我们是为"一门具体课程"做的、**计算可复现**、**每句话能翻回教材**、**答案有 8 种专用画布**的助教；
> 大多数开源项目是"通用能力"，强在学习者建模或平台化，弱在学科正确性与可审计性。**

## 4. 逐项拆解：差在哪、强在哪

### 4.1 我们明显更强的地方（护城河）

1. **学科正确性可验证**
   同类教育项目几乎都靠 LLM 生成答案；我们有 7 个确定性引擎（临界/点堆动力学/反应性/中毒/燃耗/能谱等）+ 68 条锚点测试，数字可复现、可回归。
   这是 EduChat、wendao、tutor-mcp、Notebook-LM-Mini、Socratic-Edu 都没有的（KAG 有计算算子，但需要 LLM 规划）。

2. **引用可审计到 chunk 级**
   我们每条结论给"文档 · 章节 · chunk_id · 相关度"，还有 IDF 覆盖率与门控 τ；答不出会如实说。
   大多数课程助教只给"课程页面链接"（wendao）或干脆没有（EduChat/Socratic）。

3. **8 种画布是"教学产物"而不是聊天记录**
   证据卡、计算卡、曲线、对比表、批注、测验、错题本、图谱——这些是教师/学生真正会截图、存档、交作业的东西；通用聊天平台只有 markdown。

4. **针对一门课的图谱与习题闭环**
   175 节点 / 280 边 / 24 问题链 / 112 题，章节、知识点、前置关系、配图、标准全部对齐同一门课；通用平台要从零抽。

5. **部署门槛低、可离线兜底**
   Render 免费 + Docker，mock 模式没有 LLM key 也能演示；对比 RAGFlow 4C16G、KAG/OpenSPG 多容器、LearnHouse 全栈。

### 4.2 我们明显落后的地方（按严重程度）

| # | 差距 | 对标项目 | 具体表现 | 影响 |
|---|---|---|---|---|
| 1 | **没有真正的学习者模型** | tutor-mcp（BKT+FSRS）、Notebook-LM-Mini（mastery） | 图谱节点 state 字段是静态的；做题不判分、不更新掌握度、不安排复习 | "助教"退化成"问答 + 资料库"，无法因材施教 |
| 2 | **会话不持久** | Open WebUI / LobeHub / wendao | 前端 sessions 在内存，刷新即清；后端其实已把每轮对话写进 conversations/messages，但前端没有历史接口/侧栏 | 学生不敢关页面，无法长期使用 |
| 3 | **图谱只用来"看"** | LightRAG（local/global 检索）、KAG（逻辑推理）、Notebook-LM-Mini（路径） | 175 节点/280 边没有参与召回与重排；概念题仍只靠 chunk 检索 | 多跳/前置知识类问题 recall 上限低 |
| 4 | **检索没有语义层** | RAGFlow/LightRAG/AnythingLLM | 无 embedding、无 rerank；同义表述/跨语言/公式描述召回弱 | 学生换个说法就问不到；holdout 也印证了边界 |
| 5 | **没有自动判分与错题闭环** | LearnHouse（代码自动判分）、tutor-mcp（rubric） | quiz 只有题目+解析；错题本要手动加；无掌握度回写 | 练习价值打折，"错题驱动"没闭环 |
| 6 | **没有学习路径/复习计划** | Notebook-LM-Mini（MSMS）、tutor-mcp（FSRS） | 只有"问题链"（先修关系展示），没有"下一步学什么" | 学生仍要自己决定学什么 |
| 7 | **内容生产是手工作坊** | wendao（notes→build）、LearnHouse（CMS） | 新增一章要手工维护 JSONL/图谱/习题/图 | 换课程/更新教材成本高，难复制到第二门课 |
| 8 | **无多模态输入** | LightRAG/RAG-Anything、AnythingLLM | 不能拍题/上传公式图片；只能文本提问 | 物理学生的高频场景缺失 |
| 9 | **平台能力弱**：鉴权、多用户、持久化、可观测 | Open WebUI/LobeHub/RAGFlow | Render 免费无持久盘（SQLite 会重置）；只有"账号+口令"登录，接口靠 X-Account 头，无会话鉴权；无 tracing/评测面板 | 只适合演示/小班，不适合正式开课 |
| 10 | **无 MCP / 插件生态** | tutor-mcp、KAG、LobeHub | 11 个工具只能内部用，无法被 Claude/ChatGPT 直接调用 | 生态位受限，但这也是"专注"的代价 |

### 4.3 值得注意的"同类最近邻"

**wendao 是和我们最像的项目**（课程 → 图谱 + 课程内助教 + 引用 + 教师洞察），区别：

| | wendao | 我们 |
|---|---|---|
| 内容输入 | 自动从 Markdown/Notebook/PDF 构建 | 人工整理、质量更高但不可复制 |
| 图谱 | 章节/页面/概念 + guided path | 10 章/175 知识点/280 关系 + 星图 + 问题链 |
| 回答 | LLM 只基于检索到的课程片段 | 检索 + 确定性计算 + 8 画布 |
| 正确性 | 依赖 LLM 与检索 | 计算有锚点测试，引用到 chunk |
| 教师端 | 洞察（问了什么/没答上/反馈） | 概览/用户/待复核 |
| 学习者模型 | 路径进度 | 基本没有 |
| 部署 | pip + serve，可导出单 HTML | 在线 Render + Docker |
| 许可证 | GPL-3.0 | 内部使用 |

结论：wendao 的**内容生产管线**与**教师洞察**值得学；我们的**计算正确性**与**画布产物**是它没有的。两者结合就是"下一代课程助教"。

**tutor-mcp 是最值得抄"教学内核"的项目**：它把"生成"与"确定性教学法"分开——LLM 负责讲，BKT/FSRS/前置规则负责决定下一步。我们的 7 个引擎其实已经是"确定性"的一半，缺的是"学习者状态"这一半。

## 5. 建议路线（按性价比排序）

### P0（1–2 周，改动小、收益大）

1. **会话持久化 + 历史侧栏**（对标 Open WebUI / wendao）
   - 前端 IndexedDB 存 sessions/artifacts；或直接接后端已有的 conversations/messages（聊天链路已经落库，只差历史接口）。
   - 收益：刷新不丢，学生敢长期用；也为学习者模型提供数据。

2. **学习者模型 v1（BKT-lite）**（对标 tutor-mcp）
   - quiz 作答 → 记录对错/耗时 → 按知识点更新掌握度（P(L) 简单贝叶斯）→ 回写图谱节点 state/颜色。
   - 错题自动入错题本；教师端看班级掌握度热力。
   - 不需要新基础设施，SQLite 足够；先做"每知识点 0–1 掌握度 + 最近练习时间"。

3. **GraphRAG-lite：让图谱参与检索**（对标 LightRAG/KAG，但零新依赖）
   - 检索命中 chunk → 映射到 kp → 沿 prerequisites 做 1–2 跳扩展 → 用"章/前置"做重排与上下文补全。
   - 用现有 54+26 probes 做 A/B；预期概念题、跨章题提升，计算题不受影响。

### P1（1 个月）

4. **embedding + rerank 可选后端**（bge-m3 / API embedding + cross-encoder；Hashing 兜底），保留双门控。
5. **学习路径 + 复习计划**（MSMS-lite：按图谱前置 + 掌握度排序；FSRS-lite 排复习）。
6. **图片/公式输入**（多模态 OCR/视觉模型），接现有计算引擎。
7. **MCP server**：把 11 个工具暴露成 MCP，让 Claude/ChatGPT 也能调用（对标 tutor-mcp）。

### P2（课程化/平台化）

8. **教师 CMS / 课程导入管线**（对标 wendao 的 notes→build、LearnHouse 的课程/作业/分析）：Markdown/PDF 自动抽知识点、建图、出题，人工只做审核。
9. **持久化与认证**：Render 持久盘或外部 Postgres；账号体系/班级/权限。
10. **教学分析**：未回答问题、高频误区、覆盖率趋势（wendao insights/feedback 的思路）。

### 不建议追的

- 不要为了"像通用平台"去堆模型供应商、插件市场、多频道——那不是这门课的护城河。
- 不要直接上完整 GraphRAG（LLM 抽取实体关系成本高、噪声大；KAG 的轻量构建也仍需 LLM）。我们的图谱已是结构化数据，**graph-lite 的性价比远高于重跑 GraphRAG**。

---

## 6. 一句话总结

> 开源教育项目大致分两派：**"会聊天/会陪伴"**（EduChat、Socratic、wendao）与 **"会管理学习"**（tutor-mcp、Notebook-LM-Mini、LearnHouse）；
> 我们则是第三派：**"会算、会引用、会出教学产物"**。
> 我们的短板不在"更会聊"，而在**没有把学习者的状态接进来**——补上持久化、掌握度、图谱检索这三块，就能同时具备"正确性"与"因材施教"，而不是变成又一个通用聊天壳。
