## 0. 先给结论：这套后端到底长什么样

读完 400+ 个文件里与后端相关的约 40 个源文件后，可以用一句话概括：

> **一个 FastAPI 单体（约 1200 行 Python）+ 一个以子进程方式自动拉起的、用标准库 `http.server` 写的独立 RAG 服务（约 5000 行）+ 三层"数据快照"（chunks.jsonl / graph.json / msrag.db+vectors.json）随镜像分发。Agent 用 OpenAI function calling 手写循环（不引 LangChain），事件流只有 7 种，工具靠 pkgutil 自注册。**

## 1. 进程拓扑：谁在跑，谁拉起谁

```

   │
   ├─ /            → backend/frontend_dist/index.html（React 构建产物，StaticFiles 挂载）
   ├─ /api/*       → 中间件剥掉 /api 前缀 → FastAPI 路由
   ├─ /chat        → SSE（7 事件）
   ├─ /rag/*       → httpx 反代 → 127.0.0.1:8765（RAG 服务自带后台 UI）
   └─ /health      → {ok, model, has_key, tools}

uvicorn app.main:app（backend，FastAPI）
   │
   └─ lifespan 启动时：rag_autostart.ensure_started()
          └─ 后台线程探测 127.0.0.1:8765/api/meta
```

## 2. Agent 循环（`chat.py`，全文 309 行，最重要）

### 2.1 结论先说

- **不是规则路由，是标准 OpenAI function calling + 手写 while 循环**（`client.chat.completions.create(..., tools=tool_specs, stream=True)`）。
- **最大 6 轮**（`for turn in range(config.MAX_TURNS)`），超了用 `for...else` 发 `error` 事件（`chat.py:299-300`）。
- **流式工具调用按 `index` 拼接**，工具名"只认首个非空值"、参数"必须累加"——专门为兼容不同供应商的流式行为写了注释（`chat.py:195-208`）。
- **一轮里可能同时调多个工具**：`ordered = [calls[i] for i in sorted(calls)]` 后串行执行（`chat.py:216`, `260-298`）。
- **工具异常不中断流**：catch 后把错误文本作为 `tool` 消息回灌给模型继续（`chat.py:280-298`）。
- **没有"规划→执行"两段式**，没有 planner，没有反思步，**纯 ReAct-式 tool loop**。

**流式拼装（工具调用分片是这段的核心难点）：**

```python
# chat.py:177-209
            content_parts: list[str] = []
            # index -> {id, name, args}，流式返回的工具调用需要按 index 拼接
            calls: dict[int, dict[str, str]] = {}

            async for chunk in stream:
                if not chunk.choices:
                    continue
                delta = chunk.choices[0].delta

                # deepseek-reasoner 会返回 reasoning_content；普通模型没有，跳过
                reasoning = getattr(delta, "reasoning_content", None)
                if reasoning:
                    yield thinking(reasoning)

                if delta.content:
                    content_parts.append(delta.content)
                    yield token(delta.content)

                for tc in delta.tool_calls or []:
                    slot = calls.setdefault(tc.index, {"id": "", "name": "", "args": ""})
                    if tc.id:
                        slot["id"] = tc.id
                    if tc.function:
                        # 工具名：取**首个非空值**，忽略后续重复。
                        # OpenAI / DeepSeek 只在首个分片把完整名字给一次，
                        # 但个别供应商每片都带名字 —— 用赋值会丢，用 += 会拼出重复串，
                        # 所以这里只认第一个，两种行为都能兼容。
                        if tc.function.name and not slot["name"]:
                            slot["name"] = tc.function.name
                        # 参数：必须累加，它是真的一段一段流过来的
                        if tc.function.arguments:
                            slot["args"] += tc.function.arguments
```

👉 这段注释（`chat.py:200-203`）是**全网最容易踩的坑**：不同 OpenAI 兼容供应商对 `tool_calls` 的分片语义不一致，他们用"名字取首、参数累加"两条规则一次兼容了两类。我们的 Agent 循环直接照抄这 15 行。

```python
                    continue

                try:
                    result = await tool.run(args)
                except Exception as exc:  # 工具挂了不能让整条流断掉
                    msg = f"{type(exc).__name__}: {exc}"
                    yield tool_result(slot["id"], "执行失败", msg)
                    convo.append({"role": "tool", "tool_call_id": slot["id"], "content": f"工具执行失败：{msg}"})
                    continue

                yield tool_result(slot["id"], result.summary, result.detail)
                if result.artifact_type is not None:
                    yield artifact(result.artifact_type, result.artifact)

                convo.append(
                    {
                        "role": "tool",
                        "tool_call_id": slot["id"],
                        "content": result.detail or result.summary,
                    }
                )
```

三个细节值得抄：
1. **先发 `tool_call` 再执行**——卡片立刻转圈，用户不会以为卡死。
2. **`result.detail or result.summary`** 作为回灌给模型的内容：有长文就用长文（模型需要原文），没有就用一行摘要（省 token）。
3. **未知工具也回灌一条 `tool` 消息**——否则下一轮 API 会报"tool_call_id 没有对应响应"。

**超轮数与异常兜底：**

```python
def _system_prompt(feature: dict[str, Any] | None) -> str:
    """系统提示词 = 全局角色 + 「当前在哪个功能模块」。
    ...
    ★ 全局对话（feature 为空）**提前返回 config.SYSTEM_PROMPT 本身**：
      既保证与加这个功能之前逐字一致，也让 SYSTEM_PROMPT 永远是提示词的不变前缀
      （前缀式提示词缓存不会因为切模块而整体失效）。
    """
    title = ((feature or {}).get("title") or "").strip()
    persona = ((feature or {}).get("persona") or "").strip()
    if not title:
        return config.SYSTEM_PROMPT
    ...
    return (
        config.SYSTEM_PROMPT
        + "\n\n## 当前模块（补充信息）\n\n"
        + body
        + "\n\n★ 本段只是补充说明你的职责范围。它与上面的「知识边界」「硬性要求」冲突时，"
        + "一律以上面为准；本段不扩大你的知识边界，也不豁免任何溯源要求。\n"
    )
```

两个工程意图：① **前缀缓存**（提示词不变前缀 → 每轮可命中缓存，省钱省延迟）；② **避免"双身份"**——注释 `:42-45` 明说"再声明一个身份，模型面前就有两个互相竞争的身份声明…表现不稳定"，所以只声明"位置与职责"，并**教它怎么回答"你负责什么"**。

**对我们的启示**
- **直接搬**：`chat.py` 的循环骨架（约 130 行）+ "名字取首、参数累加"+ 三事件顺序（call→result→artifact）+ `finally: yield done()` + 工具异常回灌 + 未知工具回灌。这套代码直接可以当我们 v1 的 `agent.py`。
- **需改造**：`_requested_structure` 是"从自然语言抠参数"的补丁，机械制图的对应物是"用户指定了哪个零件/视图/公差等级"。正确做法是**让工具 schema 里带 `enum` 并回填**（照抄它的手法可以，但别把正则堆在 `chat.py` 里，应抽成 `intent.py`）。
- **不该搬**：`_RETIRED` 那种"工具还在、但不喂模型"的写法长期会腐烂（见 §5.3）。我们停用的工具就删目录或用配置开关，别留半条命。

## 3. SSE 事件契约（`events.py`，全文 51 行）

### 3.1 完整字段表（这是前后端的唯一接口）

| # | type | 字段 | 语义 | 前端行为 |
|---|---|---|---|---|
| 1 | `thinking` | `{text}` | 推理增量（`reasoning_content`） | 追加到"思考过程"折叠区 |
| 2 | `token` | `{text}` | 正文增量 | 打字机追加 |
| 3 | `tool_call` | `{id, name, label, args}` | 工具开始执行 | 插卡片、转圈 |
| 4 | `tool_result` | `{id, summary, detail}` | 工具结束 | 卡片停转、显示 summary，展开见 detail |
| 5 | `artifact` | `{artifactType, data}` | 画布数据 | 按 `artifactType` 找组件渲染 |
| 6 | `error` | `{message}` | 可恢复错误 | 状态栏红字 |
| 7 | `done` | `{}` | 本轮结束 | 停表、收尾 |
| — | `[DONE]` | 裸字符串 | 流结束哨兵 | 关闭连接 |

```python
# events.py:12-37
def thinking(text: str) -> dict:
    return {"type": "thinking", "text": text}

def token(text: str) -> dict:
    return {"type": "token", "text": text}

def tool_call(call_id: str, name: str, label: str, args: dict) -> dict:
    return {"type": "tool_call", "id": call_id, "name": name, "label": label, "args": args}

def tool_result(call_id: str, summary: str, detail: str | None = None) -> dict:
    return {"type": "tool_result", "id": call_id, "summary": summary, "detail": detail}

def artifact(artifact_type: str, data: Any) -> dict:
    return {"type": "artifact", "artifactType": artifact_type, "data": data}

def error(message: str) -> dict:
    return {"type": "error", "message": message}

def done() -> dict:
    return {"type": "done"}
```

**编码方式：**

```python

def encode(event: dict) -> str:
    """序列化成一行 SSE。ensure_ascii=False 保证中文可读，方便调试。"""
    return f"data: {json.dumps(event, ensure_ascii=False)}\n\n"

Emit = Callable[[dict], Awaitable[None]]

async def stream(events: AsyncIterator[dict]) -> AsyncIterator[str]:
    async for e in events:
        yield encode(e)
    yield "data: [DONE]\n\n"
```

HTTP 头只有三条（`main.py:167-176`）：`media_type="text/event-stream"`、`Cache-Control: no-cache`、`Connection: keep-alive`，外加 **`X-Accel-Buffering: no`**——注释写得很直白："关掉 nginx 之类反代的缓冲，否则流式会被攒成一坨"（`main.py:173`）。**没有** `retry:`、**没有** event id、**没有** 心跳。

### 3.2 有没有 revision / 心跳 / 续传？

- **没有心跳**：循环里只在有内容时 yield；一次长工具调用（比如 `materials_rag ask` 最长 180s，`materials_rag:253`）期间连接是静默的。靠 `X-Accel-Buffering: no` + 前端 SSE 客户端不超时来兜。
- **没有 revision/序号**：事件不带递增 id，无法断线续传；`tool_call`/`tool_result` 靠 `id`（上游 `tool_call.id`）配对。
- **没有"步数"字段**：前端不知道当前第几轮；轮数只体现在"可能连续多张工具卡"。
- **`artifact` 与模块画布的绑定**：只有 `artifactType` 字符串 + 任意 `data`（`events.py:28-29`）。壳维护 `artifactType → FeatureModule` 的 Map（`frontend/src/lib/registry.ts:21-33`），查不到就渲染"没有功能认领"的空态（`registry.ts:44-46`）。**这条契约是"模块可插拔"的全部机制**，也是唯一会静默失效的地方（见 §10 第 9 条）。

### 3.3 契约的"人肉同步"机制

```python
# events.py:1-5

★ SSE 事件构造。与 frontend/src/lib/types.ts、README.md 的「三、契约」 三处必须同步。

```

它不是自动生成的类型，而是**三处人工同步**（Python dict / TS 类型 / README 表格）。项目里还有 `test_smoke.py` 断言事件序列（§8.2），但**没有**跨语言 schema 校验。我们如果照搬，建议多花半天把事件定义抽成一份 JSON Schema，Python/TS 各自从它生成——否则 4~8 个模块并行时，"第 8 种事件"一定会出现。

**对我们的启示**

## 5. 工具契约与 10 个工具

### 5.1 `base.py`：一个 dataclass 就是全部契约

```python
# backend/app/tools/base.py:13-21
@dataclass
class ToolResult:
    """工具的统一返回。summary 一行给折叠态，detail 展开看原文。"""

    summary: str
    detail: str | None = None
    # 需要挂到右栏画布时填。artifact_type 必须与某个前端功能注册的类型一致
    artifact_type: str | None = None
    artifact: Any = None
```

```python
# backend/app/tools/base.py:24-49
@dataclass
class Tool:
    name: str
    # 展示文案模板，用 {参数名} 占位，例如 "检索知识库 ·「{query}」"
    label: str
    description: str
    # OpenAI function calling 的 JSON Schema
    parameters: dict
    run: Callable[[dict], Awaitable[ToolResult]]

    def spec(self) -> dict:
        return {
            "type": "function",
            "function": {
                "name": self.name,
                "description": self.description,
                "parameters": self.parameters,
            },
        }

    def render_label(self, args: dict) -> str:
        """把参数填进文案模板。缺参数时退化为工具名，不抛异常。"""
        try:
            return self.label.format(**args)
        except (KeyError, IndexError, ValueError):
            return self.name
```

四字段的分工非常清晰：`summary`=折叠态一行、`detail`=模型/用户都能读的正文、`artifact_type`+`artifact`=画布数据。**`render_label` 的 try/except 是"提示词模板不能因为缺参数炸掉整个流"的防护**（并让 `chat.py` 不用加 try）。

### 5.2 注册机制：`pkgutil` 扫目录，零公共文件改动

```python
# backend/app/tools/__init__.py:21-37
def _iter_tools() -> Iterator[Tool]:
    for mod_info in pkgutil.iter_modules(__path__):
        if mod_info.name in _SKIP or mod_info.name.startswith("_"):
            continue
        module = importlib.import_module(f"{__name__}.{mod_info.name}")
        tool = getattr(module, "TOOL", None)
        if tool is None:
            print(f"[tools] 跳过 {mod_info.name}：没有导出 TOOL")
            continue
        yield tool

TOOLS: dict[str, Tool] = {}
for _t in _iter_tools():
    if _t.name in TOOLS:
        raise RuntimeError(f"工具名重复：{_t.name}。每个工具名必须全局唯一。")
    TOOLS[_t.name] = _t
```

- **新工具 = 建目录 + `__init__.py` 导出 `TOOL`**，不改任何公共文件。
- 重名直接 `RuntimeError`（启动即炸，而不是运行期覆盖）。
- 与前端对称：前端用 `import.meta.glob('../features/*/index.ts')` 自动注册（`registry.ts:12-19`）。
- 同名约束还有一道脚本校验：`scripts/check-boundaries.py:145-170` 检查"工具 `name` 与文件夹名一致"、"每个目录都有 `__init__.py` 且导出 `name=`"，不一致就红。**这是"文档规则 → 可执行规则"的典范**（`check-boundaries.py:14-15` 原话："光写在文档里的规则会被违反，能跑出红字的规则不会"）。

2. **`action` 参数是它们处理"工具太多"的通用手法**：`materials_rag` / `mistake_book` 都用 `action` 做二级路由。
3. **artifact 形状是 camelCase**（`chunkId`、`documentTitle`、`hardnessHrc`），与 Python 侧 snake_case 刻意区分——这是"跨语言契约"的边界标记（`main.py:104-115` 的 `FeatureContext` 字段也做了注释）。

## 6. 知识边界到底怎么实现的（三道闸，但只有一道是硬的）

### 6.1 三道闸的分工

| 闸 | 位置 | 机制 | 强度 |

| ① **检索门控** | `search_knowledge._run` | IDF 加权覆盖率 < 0.50 → 直接返回"知识库未收录"，**不把任何原文喂给模型** | **硬**（代码强制） |

**分词**（中文 2-gram，英文按词，数字整体）：

```python
# search_knowledge:52-63
# 英文按单词、数字整体保留（「250 目」的 250 是个有意义的词）、中文按 2-gram
_TOKEN_RE = re.compile(r"[A-Za-z][A-Za-z0-9\-]*|\d+|[一-鿿]{2,}")

def _tokens(text: str) -> list[str]:
    """粗分词：英文按单词，中文按 2-gram 滑窗。够用且不引依赖。"""
    out: list[str] = []
    for piece in _TOKEN_RE.findall(text):
        if piece[0].isascii():
            out.append(piece.lower())
        else:
            out.extend(piece[i : i + 2] for i in range(len(piece) - 1))
    return out
```

**疑问词过滤**（否则"是什么"会把库内问题的覆盖率拉垮）：

```python
# search_knowledge:66-81
# 疑问词/语气词。中文 2-gram 会把「什么」「怎么」「是什」「么要」切成大量
# 与知识无关的碎片；它们几乎不可能出现在语料里，却会把查询覆盖率拉低，
# 导致「库内问题」分数虚低。查询侧过滤掉它们，语料侧保留原样（IDF 不重算）。
_STOP_CHARS = set("什么怎么是为的了呢吗吧啊哪谁这那与否")

# 这些词含「为 / 的」等虚词，但本身是课程里的实义词。
# 只按字符过滤会把「目的」「行为」误删，导致「实验目的是什么」检索跑偏。
_CONTENT_WORDS = {"目的", "行为", "为了", "目的性"}
```

**IDF**（未见词按最高稀有度计——这就是"库外信号"）：

```python
# search_knowledge:171-187
@lru_cache(maxsize=1)
def _idf() -> dict[str, float]:
    """每个词在知识库里的稀有度（IDF）。

    ★ 这是让「知识库未收录」这个问题能被正确拒绝的关键。
    没有它，「工艺」这种在材料学文本里到处都是的 2-gram 会让
    「铝合金焊接工艺」这种库外问题拿到虚高的分数，模型就会以为检索到了东西然后编答案。
    """
```

**打分公式**（**注意：它不是纯覆盖率，而是"覆盖率 × 章节权重 × 提示加成"**）：

```python
# search_knowledge:190-236
def _score(query_terms: list[str], chunk: dict, query: str = "") -> float:
    """IDF 加权的**查询覆盖率**：query 里有多少（按稀有度加权的）词被这个块覆盖了。
    ...
    ★ 查询侧的疑问词/语气词先过滤（见 `_content_tokens`）。否则「位错滑移是什么」
      里的「什么」「是什」「移是」会白白拉低覆盖率，把库内问题误判成库外。
    """
    uniq = {...}
    if not uniq:
        return 0.0

    rows = _load()
    idf = _idf()
    # 语料里从没出现过的词，按最高稀有度算 —— 它们正是「库里没有」的信号
    default_idf = math.log(len(rows) + 1) if rows else 1.0

    total = sum(idf.get(t, default_idf) for t in uniq)
    if total <= 0:
        return 0.0

    bag = set(_tokens(chunk["text"]))
    # 把 doc / experiment / section 也计入匹配：问「实验一的实验目的是什么」时，
    # 「实验一」只出现在 metadata 里，不加入的话真正的那条会被别的段落挤掉。
    meta = chunk.get("metadata", {})
    bag.update(_tokens(f"{meta.get('doc', '')} {meta.get('experiment', '')} {meta.get('section', '')}"))

    hit = sum(idf.get(t, default_idf) for t in uniq if t in bag)

    coverage = hit / total
    section = chunk["metadata"].get("section", "")
    weight = SECTION_WEIGHT.get(section, 1.0)
    boost = 1.0
    if query:
        hints = SECTION_HINTS.get(section, ())
        if any(hint in query for hint in hints):
            # 「目的/意义」类问题优先给实验目的段落；其他章节提示只做温和加成。
            boost = 2.0 if section == "实验目的" else 1.6
    return coverage * weight * boost
```

其中 `SECTION_WEIGHT`（`search_knowledge:31-38`）：实验原理 1.4 / 实验内容 1.3 / 注意事项 1.2 / 材料设备 1.0 / 实验目的 0.8 / 报告要求 0.6。

⚠️ **技术后果（项目书没提）**：`coverage ∈ [0,1]`，乘上 `1.4×2.0=2.8` 后 **`_score` 最大值可达 2.8**，所以：

- 它**不再是"覆盖率"**，而是"加权覆盖率"；项目书/README 里的"库内最低 0.654、库外最高 0.361"是 `_score` 的值，不是裸覆盖率；
- 阈值 0.50 的实际含义随**章节分布**漂移：同一问题命中"实验目的"段时 0.25 的覆盖率就能过闸（被 ×2 顶到 0.5），命中"实验报告要求"段时要 0.83；
- 我们复刻时若照抄这套乘法，就必须用**我们自己的探针**重标定，不能照抄 0.50。

**执行**：

```python
# search_knowledge:257-270
    terms = _content_tokens(query)
    ranked = sorted(rows, key=lambda c: _score(terms, c, query), reverse=True)
    # ★ 低于阈值的一律不要 —— 宁可回答「知识库未收录」，也不能拿不相干的原文
    #   喂给模型然后被编成答案。这是「不编造」这条硬要求的实现点。
    hits = [c for c in ranked if _score(terms, c, query) >= MIN_COVERAGE][:top_k]

    if not hits:
        return ToolResult(
            summary="知识库未收录",
            detail=(
                f"以「{query}」为关键词没有检索到任何内容。"
                "请如实告诉学生知识库中未收录这个问题，并给出最接近的相关条目，不要编造。"

```

### 6.3 探针：`retrieval_probe.py` 怎么判"库内命中、库外拒绝"

**判据不是主观评价，是三个可执行的断言**（`retrieval_probe.py:78-146`）：

```python
# retrieval_probe.py:110-127
    lo_in = min(s for _, s in in_scores)
    hi_out = max(s for _, s in out_scores)

    print(f"  库内最低：{lo_in:.3f}   库外最高：{hi_out:.3f}   阈值：{MIN_COVERAGE:.3f}")

    if lo_in > hi_out:
        margin = lo_in - hi_out
        print(f"  √ 分得开，余量 {margin:.3f}")
        print(f"    阈值可用的安全区间：({hi_out:.3f}, {lo_in:.3f})")
    else:
        print(f"  × 分不开！库外最高分超过了库内最低分")

    bad = bool(miss) or bool(false_alarm) or lo_in <= hi_out
```

- **探针集**：`IN_SCOPE` **26 条**（`retrieval_probe.py:24-53`）、`OUT_OF_SCOPE` **10 条**（`:55-67`），后者包含"铝合金焊接工艺 / Python 怎么写文件 / 写一首关于春天的诗 / 手机电池怎么充电"等**近域干扰**（前两条尤其刁钻："铝合金"和课程材料撞词、"写文件"考察通用能力）。
- **输出**：逐题打印分数 + √/×，最后打印**"库内最低 / 库外最高 / 阈值 / 安全区间"**，退出码非 0 表示"分不开"。
- **可操作性**：结尾直接给三步修法（`retrieval_probe.py:138-141`）——"库内被误拒→调低阈值或补 aliases；库外被误收→调高阈值；两者分不开→改 `_score`，而不是调阈值"。
- **不依赖 API Key、不依赖网络**（`retrieval_probe.py:4-5`），可进 CI。

**它和 `materials_rag` 的关系：几乎没有关系（这是最大盲点）**

- `search_knowledge` 读 `data/chunks.jsonl`（163 块，含劳育公开摘编），**有门控**；
- `materials_rag` 走 8765 的 RAG 服务，读 `msrag.db`（15 文档/117 子块），**没有覆盖率门控**（`rag-system/core/config.py:164` `min_relevance: float = 0.0`，即不设下限）；
- 两者的去重/评分/阈值完全不共享；探针只测前者。

也就是说：**"知识边界门控"只保护了其中一条检索链路**。如果模型选了 `materials_rag`（它的 description 写着"优先用 action=search"），拿到的是无阈值过滤的结果，只能靠提示词兜。**这是"两个 RAG 栈并行"的直接代价。**

### 6.4 我对这套边界机制的评价

**好的地方**：把"拒答"做成了**检索层的返回**，而不是提示词里的请求；探针把"阈值该多少"变成可复现的实验；`default_idf = log(n+1)` 用"未见词按最稀有"给库外问题判死刑——这个思路非常实用，值得直接搬。

**问题**：阈值指标被 `SECTION_WEIGHT × boost` 污染（§6.2）；探针只覆盖本地链路；语料扩到 163 块后注释还停留在 116（`search_knowledge:24`、`knowledge/README.md:73`），说明**阈值没有随语料重标定**（或至少没有更新记录）——这正好是它自己警告的"语料一变就要重跑"。

**对我们的启示**
- **直接搬**：`retrieval_probe.py` 的整个骨架（26+10 探针 → 打分离带 → 退出码）和 `default_idf` 的"未见词即最稀有"。
- **需改造**：① 把 `_score` 拆成"纯覆盖率"与"排序加成"两层——**阈值只作用于纯覆盖率**，排序加成不影响是否拒答；② 探针集要扩到**机械制图专属干扰项**（"焊接符号""齿轮模数""液压原理"——同属机械但不属制图课）；③ 两条检索链路（本地 + RAG 服务）必须**共用同一个门控**，或者干脆只留一条。
- **不该搬**：`SECTION_WEIGHT` 这种"按章节名调权"的做法。机械制图的章节名是"投影法/组合体/剖视/零件图"，权重应来自"答案通常在哪类章节"，且必须能解释；照抄材料课的数值没有依据。

## 7. RAG 服务（`rag-system/`，独立进程，8765）

### 7.1 为什么要把 RAG 拆成独立服务（代码与注释里的真实原因）

1. **它是从一套工业级 RAG 系统里"抽出来的插件"，不是为本项目新写的**。`rag-system/README.md:3-7` 原文：

   > "从一套成熟的工业级 RAG 系统中抽出来的**插件版**：保留完整的 RAG 全流程，换掉主题（材料科学），简化掉登录/用户/管理员/审批，并把重型基础设施（PostgreSQL + Milvus + etcd + MinIO + bge-m3 微服务）换成了可嵌入的轻量实现。一句话：**拷走即用**。"

2. **"不改原系统一行代码"是硬约束**。`rag_autostart.py:5`、`main.py:65` 都写着这句。拆成独立进程 + HTTP 反代，是"复用而不侵入"的最省事路径：原系统的 Web 后台（`rag-system/web/`）也能通过 `/rag/` 直接挂出来给教师用（`main.py:59-87`）。
3. **重依赖与主服务隔离**。PP-StructureV3 需要 Python 3.9–3.11 + paddlepaddle（GB 级），主服务跑 3.12/3.13（`README.md:173-177`）。**跨解释器**只能靠子进程，所以它把 `ppsv3/rag.py` 当**外部 CLI** 调用（`rag/parsers/ppsv3_adapter.py`），而整个 RAG 服务就是这个思想的延伸。
4. **可选降级**：RAG 服务可以完全不启动（`MSRAG_AUTOSTART=0`），主服务只是少一个工具；反之 RAG 服务也能独立给别人用（有 SDK、有 Function Calling schema、有命令行）。
5. **演示体验**：评委不该双击 `启动.bat`（`rag_autostart.py:2-4`）→ 自动拉起 + 脱离子进程 + 日志写 `/tmp`。
6. **部署现实**：单容器里跑两个进程，共用一个对外端口（`Dockerfile:23-27`），"整站共用一个对外端口"。

> **一句话**：拆服务不是因为"微服务更先进"，而是因为**它是一段不能改的外部代码 + 需要另一个 Python 版本 + 允许不存在**。这三个约束，机械制图项目里一个都不成立（我们自建 RAG，同一解释器），所以**不该照抄这个拆分**——但"重计算/异解释器/可缺失的能力放子进程"这条原则要抄。

### 7.2 通信方式与协议

- **HTTP over 127.0.0.1:8765**，标准库 `urllib`（主服务侧 `materials_rag:47-58`）与 `urllib.request`（RAG 侧 `rag/llm.py`）都不引 HTTP 客户端依赖。
- **统一响应信封**：`{"success": true, "data": ..., "request_id": "req_..."}`；失败 `{"success": false, "error": {"code","message"}}`（`README.md:345-346`）。
- **主服务只用 6 个接口**（`materials_rag:9-15`）：`GET /api/meta`、`POST /api/search`、`POST /api/ask`、`GET /api/documents`、`GET /api/chunks/{id}`、`POST /api/documents/text`。
- **RAG 服务自己的后端是标准库 `http.server`**（`server/http_api.py`，1009 行，`BaseHTTPRequestHandler` 手写路由 + multipart 解析 + 手写 SSE），完全零 Web 框架依赖（`README.md:37-38`："核心功能对第三方包零依赖，不装也能跑"）。
- **它自己的 SSE 事件是 4+1 种**：`meta → retrieval → delta* → done`，异常 `error`（`README.md:372`；实现 `rag/pipeline.py:443-539`）。
- **主服务这一侧不消费 RAG 的 SSE**：`materials_rag` 只用非流式 `/api/ask`（`materials_rag:253`），把答案整段塞进 `detail` 回灌给对话模型。所以用户在 UI 上看到的"逐字流出"来自**主 Agent 模型**，不是 RAG 模型——**RAG 的流式能力在集成时被丢掉了**（可优化点）。
- **无鉴权**：只监听 127.0.0.1 且主服务反代，安全边界靠"本机 + CORS 默认同源"（`README.md:374-379`）。

### 7.3 分块：真正的"父子双层"在这里

```python

"""父子双层分块器（移植自原项目 chunk_service，参数可配置）。

为什么是"父子双层"？
    - **子块**（chunk）：真正写入向量库的检索单元，粒度小、语义集中，检索准。
    - **父块**（section）：章节级上下文，不参与检索，但在生成时用于补齐背景、
      在溯源时用于定位"这段证据属于哪个章节"。
只做单层切分时，答案常因缺少章节背景而失真；双层是原项目验证过的做法。
"""
```

```python

                 min_chunk_tokens: int = 30):

```

**流程**（`chunker.py:45-100`）：

1. `_build_sections()` 按"标题块"切章节（`_is_heading`：`block_type == "title"`、长度 ≤60 且命中摘要/引言/实验方法等关键词、或 label 是 h1~h6）→ `(title, path, level, blocks)`；
2. 每个章节 = **1 个父块**（`ParentChunk`，字段含 `parent_key`、`section_id`、`section_path`、`level`、`page_start/end`、`child_count`、`preview`）；
3. 章节内 `_expand_segments()` 把超 700 token 的段落硬切（带 `limit//8` 重叠）；
4. `_pack()` **贪心装箱**到 700 token，块间保留 120 token 尾部重叠（`_tail_tokens`）；
5. 尾巴 < 30 token 时**并进上一块**（避免碎片）；
6. 子块 `chunk_id = f"chk_{document_id}_{section_no:04d}_{idx:04d}"`（`chunker.py:85`）——**这就是项目书里 `chk_doc_…` 的来源**，实测形如 `chk_doc_a163fb06774ffd660e_0001_0000`；
7. 图：`_extract_images()` 从正文里抽 `![...](/api/assets/...)` → 子块 `images` 字段（`chunker.py:263-279`）；**检索时若该段无图，用"同页配图"兜底，每段最多 3 张**（`pipeline.py:374-393`）。

**实测结果**（`msrag.db`）：15 文档 → **56 父块 / 117 子块**，子块长度 57~984 字、均值 479 字。与项目书"56 父块 / 117 子块"**完全对得上**——但注意这是在 **RAG 服务**里，不是本地 `chunks.jsonl`（163 块，见 §10）。

### 7.4 检索：BM25 + 稠密，归一化后加权

```python
# rag/vectorstore.py:33-35
_BM25_K1 = 1.5
_BM25_B = 0.75
_INDEX_VERSION = 1
```

```python
# rag/vectorstore.py:280-304
    def hybrid_search(self, query: str, query_vec: Sequence[float], top_k: int,
                      document_ids: Optional[Iterable[str]] = None,
                      sparse_weight: float = 0.35,
                      enable_sparse: bool = True
                      ) -> List[Tuple[str, float, float, float]]:
        """返回 [(chunk_id, 融合分, 稠密分, 稀疏分)]。"""

        fetch = max(top_k * 3, top_k + 10)
        dense = dict(self.dense_search(query_vec, fetch, document_ids))
        sparse = dict(self.bm25_search(query, fetch, document_ids)) if enable_sparse else {}

        dense_max = max(dense.values(), default=1.0) or 1.0
        sparse_max = max(sparse.values(), default=1.0) or 1.0
        dense_w = 1.0 - sparse_weight

        keys = set(dense) | set(sparse)
        results: List[Tuple[str, float, float, float]] = []
        for key in keys:
            d_score = dense.get(key, 0.0) / (abs(dense_max) or 1.0)
            s_score = sparse.get(key, 0.0) / (abs(sparse_max) or 1.0)
            fused = dense_w * d_score + sparse_weight * s_score
            results.append((key, fused, dense.get(key, 0.0), sparse.get(key, 0.0)))
        results.sort(key=lambda item: item[1], reverse=True)
        return results[:top_k]
```

- **候选池**：`fetch = max(top_k*3, top_k+10)` —— 两路各多取 2~4 倍再融合，避免"某一路排名靠后的好块被截掉"。
- **归一化**：各自除以本路最大分（不是 min-max、不是 softmax）——**简单但没有下界**，若某路全为噪声，最大分也会成 1.0。可改进点。
- **BM25**（`vectorstore.py:252-278`）：标准 Robertson/Zaragoza 公式，`idf = log(1 + (N-df+0.5)/(df+0.5))`，中文按 2-gram + 单字（`text_utils.py:46-86`），单位/希腊字母整体保留。
- **稠密**（`vectorstore.py:207-249`）：**纯内存线性扫描**，有 numpy 就矩阵化；`O(块数×维度)`，注释明确"几万段落内毫秒级，再大就该换回 Milvus 了"。
- **落盘**：整份索引 JSON（`vectors.json`，含每条 `doc/vec/text/tf/len`），`mkstemp + os.replace` 原子写（`vectorstore.py:116-121`）；读写用 `RLock`（`:38-51`），注释写明"不加锁检索会撞上 dictionary changed size during iteration"。
- **过滤**：`pipeline.search` 里 `if fused < self.settings.min_relevance: continue`（`pipeline.py:351-352`），而 `min_relevance` 默认 **0.0**（`core/config.py:164`）→ **RAG 侧没有拒答闸**。

### 7.6 生成、引用与降级

**提示词**（`rag/prompts.py:16-36`）：只依据 `[证据 N]`、证据不足就说不足、不编造 chunk_id/页码/DOI、单位照抄、术语四要素主线。

**引用（保守策略，值得抄）**：

```python
# simulate_heat_treatment:48-54
def _carbon_factor(carbon: float) -> float:
    """教材那条曲线本身就是 45 钢（0.45%C）的实测值，所以 0.45 处**不能**再修正，
    否则等于把基准重复扣一次（曾导致 200℃ 回火算成 53 HRC，落在教材 57–60 之外）。
    只在偏离 0.45 时按亚共析钢淬火硬度的经验趋势做温和修正。"""
    if carbon >= 0.45:
        return 1.0
    return 0.4 + 0.6 * (carbon / 0.45) ** 0.5
```

模型的三层结构：
1. **查表 + 线性插值**（`_interp`，`:36-45`）——不做回归拟合，因为"教材只给了区间端点"；
2. **偏离基准才修正**（`_carbon_factor`）——记录了一次真实事故（重复扣减 → 53 HRC）；
3. **矛盾显式化**（`OVERLAP_NOTE` + `warning` 字段 + 480~540℃ 区间触发提示，`:145`）——不假装教材是自洽的。

## 10. 与项目书 / README 的不一致清单（**这节最重要**）

## 11. 值得复刻的 10 条清单（按性价比排序：收益/工作量）

> 评分口径：收益 = 对"能跑、能看、能过评审"的贡献；工作量 = 单人完成所需时间。**排序 = 收益/工作量 从高到低。**

| 排名 | 要复刻的东西 | 工作量 | 收益 | 为什么排这个位置 |
|---|---|---|---|---|
| 1 | **7 类 SSE 事件 + `ToolResult` 四字段 + `artifactType` 契约** | 0.5 天 | ★★★★★ | 一切并行开发的地基；行数最少、约束最强。附带把"事件 schema 生成"做了（比它更稳） |
| 2 | **工具自注册（pkgutil）+ 命名对称 + 边界检查脚本** | 0.5 天 | ★★★★★ | 新增工具零公共文件改动；`check-boundaries.py` 200 行挡住 80% 的协作事故 |
| 3 | **`SYSTEM_PROMPT` 的五段结构**（边界枚举/越界话术/溯源模板/未收录话术/不完整数据处置） | 0.5 天 | ★★★★★ | 纯文本，却是"教学 Agent 像助教"的最大来源；直接按机械制图改写即可 |
| 4 | **Agent 循环骨架**（function calling + 流式拼接 + 三事件 + 异常/未知工具回灌 + `finally done`） | 1 天 | ★★★★★ | 约 130 行，抄完 v1 就能跑；两个"供应商差异"的坑它已经替我们踩了 |
| 5 | **冒烟测试三件套**（数值锚点 / Agent 循环假客户端 / 自动注册与提示词逐字断言） | 1 天 | ★★★★☆ | 让"改坏了"立刻可见；假客户端让 Agent 循环可回归、零 API 成本 |
| 6 | **检索门控 + 边界探针**（IDF 覆盖率 + `default_idf=log(n+1)` + 26/10 探针 + 分离带打印） | 1.5 天 | ★★★★☆ | "会拒答"是最容易被评审记住的点；探针让阈值可辩护。**注意把加成从阈值里剥离** |
| 7 | **父子双层 chunker + `chk_{doc}_{sec:04d}_{idx:04d}`** | 1.5 天 | ★★★★☆ | 引用可信度的来源；编码可反查、可排序 |
| 8 | **混合检索（BM25 + 稠密，归一化加权，候选池 `max(3k,k+10)`）** | 1.5 天 | ★★★☆☆ | 术语/符号密集的制图课收益明显；但**要先决定嵌入是否真语义**，否则两路都是词法 |
| 9 | **三级降级 + 如实标注**（嵌入/生成/解析都降级，且界面明示当前模式） | 2 天 | ★★★☆☆ | 演示保险；也是"诚实"加分项。工作量在"把降级状态透到 UI" |
| 10 | **发布形态**（单容器 + 预建索引随镜像 + `/health` 报能力 + `/rag` 反代 + 自动拉起子服务） | 2 天 | ★★★☆☆ | "打开就能用"是评审的隐性门槛；索引随镜像这点很多人会漏 |

**明确不要复刻的 5 样**（省下的时间比上面任何一条都值钱）：

1. **双 RAG 栈**（`search_knowledge` 本地索引 + `materials_rag` 远程索引）——两套语料、两套评分、一套有门控一套没有。
2. **`_RETIRED` 半死工具**——停用就删。
3. **`artifact_type="knowledge"/"micrograph"` 这种悬空类型**——CI 校验。
4. **提示词里复写数值区间**——单一真相源放代码+测试。
5. **`SECTION_WEIGHT × boost` 与阈值混用的评分**——阈值只看覆盖率，加成只影响排序。

## 13. 最后：如果只能记一句话

> **这套后端的可复用价值不在"它用了什么模型"，而在"它把不确定性都变成了可执行的检查"**——工具坏了降级、服务没起就拉起、语料变了跑探针、数值改了跑断言、边界越了有脚本报红。我们做机械制图，照这个"把一切变成可检查项"的路子做，RAG 用什么算法反而是最不重要的。
