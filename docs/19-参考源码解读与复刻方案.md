## 二、七条必须照抄的设计（这些是他们真正值钱的地方）

### 1. 模块即插件：加模块不改壳一行代码

前端 `lib/registry.ts` 用 `import.meta.glob('./features/*/index.ts')` 扫目录；
每个模块 `index.ts` 默认导出：

```ts
export default {
  id: 'feynman',          // 必须等于文件夹名
  title: '费曼追问',
  persona: '负责…',        // 可选：随请求发给后端，拼进系统提示词
  artifactTypes: ['feynman'],  // 全局唯一，类型就是 string（故意不做联合类型）
  order: 80,              // 左栏排序
  preview,                // 样例数据，无后端也能看效果
  autoOpenCanvas: true,   // 可选：产出 artifact 时是否自动展开右栏
  Component,              // 画布模式
  page,                   // 可选：整页模式
} satisfies FeatureModule
```

后端 `tools/__init__.py` 用 `pkgutil` 扫 `tools/*/`，`__init__.py` 导出 `TOOL` 即被发现。

> **为什么重要**：模块会换（他们换过好几轮：module3→mistakeBook，module5/6 已删）。
> 把注册表写死在壳里，每换一次就要动共享文件，必然打架。

### 2. 三栏工作台 + 「工具调用卡片」是 Agent 观感的灵魂

`shell/ToolCallCard.tsx` —— 折叠态显示 `summary`、展开看 `detail`、调用中转圈。
`AGENTS.md` 里原话：

> 「三栏工作台、工具调用卡片、流式回答 —— 这些是「这是个 Agent」的视觉证据。
> 如果整页界面看起来只是普通网页，**评委就看不到"Agent"在哪了**。」

→ 整页模式的模块必须自己留一个「智能问答」tab，把工具卡片和流式回答露出来。

### 3. 七种 SSE 事件，不许加第八种

| type | 载荷 | 前端行为 |
|---|---|---|
| `thinking` | `{text}` | 追加到「思考过程」折叠区 |
| `token` | `{text}` | 打字机追加正文 |
| `tool_call` | `{id, name, label, args}` | 插入工具卡片，转圈 |
| `tool_result` | `{id, summary, detail}` | 停转圈，显示摘要 |
| `artifact` | `{artifactType, data}` | 挂到右栏画布 |
| `error` | `{message}` | 状态栏红色提示 |
| `done` | `{}` | 结束本轮 |

（我们已对齐，含 `error`。）

### 4. 工具契约：一个类 + 一个返回值

```python
TOOL = Tool(
    name="你的工具名",      # 必须等于文件夹名
    label="展示文案 · {参数名}",
    description="给模型看的说明，写得越清楚它越知道何时该调",
    parameters={"type": "object", "properties": {}, "required": []},
    run=_run,
)
# run 返回 ToolResult(summary, detail, artifact_type=..., artifact={...})
```

**组件里不许自己发网络请求**，要数据就 `onSendMessage()` 让 Agent 去调工具 ——
这样所有可视化走同一条链路，录屏时评委能看到 Agent 真的在干活。

### 5. `preview.ts`：没有后端也能看效果

每个模块必须带样例数据，画布空态点「查看样例数据」就渲染，右上角标「预览数据」。
→ 好处：前端可以完全脱离后端开发；演示时后端挂了也能讲。

### 6. 知识边界 = 封闭语料 + 检索探针

`backend/tests/retrieval_probe.py` 同时验证两件事：**库内的能命中、库外的能拒绝**。
（我们的 `eval/run.py` 是同一思路，但我们的探针集只有 54 题且被用来调参了。）

### 7. 数值必须有教材依据 + 锚点测试

`simulate_heat_treatment` 的每个数值都能追溯到教材，`test_smoke.py` 逐点校验是否落在教材区间。
`AGENTS.md` 记了两个真实翻车案例（0.45%C 处重复修正把 200℃ 回火算成 53 HRC；500℃ 中温/高温重叠）。
→ 和我们的「能算的绝不让模型背」是同一哲学，但他们的**测试方式**更狠：锚点区间断言。

## 六、★ 参考作品的遗留债：这些**不要照抄**（源码实测）

读完 `backend`/`frontend` 源码后发现的坑。项目书里写的和代码实际做的不一致，
**复刻时以代码为准，但代码里的遗留部分正是我们要绕过的地方**。

### 1. 10 个工具，实际只给模型 7 个

`tools/__init__.py:41-49` 有一个 `_RETIRED` 集合，3 个工具被过滤掉，不进 `specs()` 喂给模型：
它们对应的前端模块已经移除，工具保留只是为了冒烟测试和直接调用。

> **最刺眼的一条**：项目书把「教材数值约束的物理建模（45 钢回火曲线）」写成**创新点 3**，
> 但这个 `simulate_heat_treatment` 工具**已经被退役**，前端模块也移到 `reference/` 不在左栏。
> 也就是说：**它的核心卖点在最终产品里根本没被调用。**

→ **对我们是直接的警告**：我们的公差/螺纹/圆弧/投影/剖切引擎**必须确认真的在对话链路里被调用**，
不能只活在测试脚本里。这一条我已经在 `verify_all.py` 之外单独核过：11 个工具都在 `_plan()` 可达路径上。

### 2. 两套 RAG 栈并存

| | 本地 `search_knowledge` | 独立 RAG 服务（`materials_rag`） |
|---|---|---|
| 索引 | `data/chunks.jsonl` **163 块扁平**，无父块 | `msrag.db` 15 文档 / **56 父块 / 117 子块** |
| 门控 | ✅ 有（`MIN_COVERAGE=0.50`） | ❌ **没有**（`min_relevance=0.0`） |
| 检索 | BM25 + IDF 覆盖率 | BM25 + 稠密，归一化加权 |

项目书把两套混着说，导致「父子双层切分」和「覆盖率门控」看起来像同一个系统的两个特性，
实际是**两条独立链路，只有一条有门控**。

→ **我们必须只有一条检索链路**，父子结构和门控做在同一处。（我们现在就是一条，保持不动。）

### 3. 所谓"语义向量"其实是 512 维哈希词袋

`vectors.json` 实测 `dim=512`；要真语义必须配 `MSRAG_EMBEDDING_API_KEY` 并重建索引。
随包交付的是**词法级**哈希向量。

→ 我们方案里写的"混合检索"必须写清：**BM25 + 哈希 TF-IDF**，不是神经嵌入。
我们 `docs/04`/`docs/09` 一直是这么写的 ✅

### 4. 前端有两个 artifactType 没人认领

`search_knowledge` 返回 `artifact_type="knowledge"`、`diagnose_micrograph` 返回 `"micrograph"`，
但前端 `features/*/index.ts` 里没有这两个类型 → 画布会显示「没有功能认领」。

→ **我们该做的检查**：在 CI 里断言「后端每个 `artifact_type` 都有前端 owner」。
我们现在 `KNOWN_CANVAS_TYPES` 与后端 `ARTIFACT_TYPES` 是两份手写清单，容易漂移。

### 5. 注释会腐烂，统计数字别手写

`search_knowledge` 注释写"语料 57→116 块"，实际 **163 块**；README 里的行数、工具数、文档数
都有类似偏差。

→ **我们的统计一律由脚本生成**（我们 `verify_all.py` 已经是运行时实测，不写死 ✅）。

### 6. 指标定义要写清楚

他们的探针报"课内 26/26 全召回、课外 10/10 全拒答"，
但 `_score` 里含 `×1.4 ×2.0` 的加权加成，报告里说的"覆盖率"其实是**加权分**，不是纯覆盖率。

→ 我们的 held-out 0.974 用的是**纯覆盖率阈值**，指标定义在 `docs/09` 里写清了 ✅
但还要补一句：τ=0.55 是作用在"过滤虚词后的内容词覆盖率"上，不是原始字符覆盖率。

## 七、结论：这次复刻的取舍

| 复刻 | 不复刻 |
|---|---|
| 插件化模块契约 + 自动注册 + 脚手架 + 边界检查 | 两套 RAG 栈 |
| 三栏壳 + 工具调用卡片 + 整页模式 | `_RETIRED` 式的"测试专用工具" |
| `feature:{id,title,persona}` 拼进提示词 | 512 维哈希冒充"语义向量" |
| `SYSTEM_PROMPT` 五段结构 | 悬空的 artifactType |
| 数值锚点区间断言式测试 | 手写统计数字 |
| 每模块 `AGENTS.md` 任务书 | 把"退役功能"当卖点 |
| `preview.ts` 无后端可看 | — |

**一句话**：参考作品值钱的是**架构和工程约束**，不是它的功能清单——
功能清单里有相当一部分是"设想过但没落地/已退役"的。
我们复刻它的骨架，但把我们自己的确定性引擎（真几何、真剖切、真找错）做扎实，那才是我们的差异点。

### 任务书漂移是**系统性问题**，不是个别笔误

- `module1/AGENTS.md` 写 `type`、代码是 `kind`；
- `module4/AGENTS.md` 至今仍是「【待填】全部待做」的空模板；
- `search_knowledge` 注释写「语料 116 块」、实际 163 块；
- README 说「工具 10 项」、实际只喂模型 7 个。

> **对我们的直接启示**：我们给 9 个模块写 `AGENTS.md` 任务书时，
> **数据形状必须从代码里生成或校验**，不能手写后就不管。
> 建议做一个 `scripts/gen-module-docs.py`：从 `types.ts` / `index.ts` 抽出真实字段，
> 生成任务书的「数据形状」一节 —— 让文档永远跟着代码走。
