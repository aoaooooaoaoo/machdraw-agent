# 21 · 后端工具自注册改造记录

> 目标：把后端工具从「一个 `__init__.py` 硬编码 11 个函数 + `TOOLS` 字典」改成
> 「`pkgutil` 扫描 `tools/*.py`，每个工具模块导出 `TOOL` 即自动发现」，
> 做到**新增一个工具不用改任何公共文件**，与前端 `features/<id>/index.ts` 自注册对齐。
>
> 本次只换**注册机制**，不换路由逻辑：`orchestrator._plan()` 与 `main.py` 一行未动。

---

## 1. 改造动因

| 维度 | 改造前 | 改造后 |
| --- | --- | --- |
| 新增工具 | 在 `tools/__init__.py` 加函数 + 在 `TOOLS` 字典登记（改公共文件） | 新建 `tools/<name>.py` 导出 `TOOL`，**不改公共文件** |
| 工具元数据 | 只有 `TOOL_LABELS` 一张短标签表 | 每个工具自带 `label / description / parameters`（JSON Schema） |
| 模型可调用性 | 没有参数 schema，只能靠代码里写死的编排规则 | `TOOL.parameters` 可直接喂给 LLM function calling |
| 一致性保障 | 无（函数与字典可能对不上） | 启动时三条硬校验，违反**直接 raise** |
| 与前端架构 | 前端已自注册，后端仍是硬编码 | 两侧都自注册，骨架对齐 |

## 3. `pkgutil` 自注册核心（约 20 行）

`app/tools/__init__.py` 的核心逻辑（省略报错文案）：

```python
import importlib
import pkgutil

from ..rag.symbols import extract_fit_spec, extract_thread_spec
from .base import EVIDENCE_CONSTRAINT, ToolContext, ToolOutcome
from .spec import ToolSpec

_SKIP_MODULES = frozenset({"__init__", "base", "spec"})   # 非工具模块


def discover() -> list[ToolSpec]:
    specs, seen = [], {}
    modules = sorted(info.name for info in pkgutil.iter_modules(__path__))
    for name in modules:
        if name in _SKIP_MODULES or name.startswith("_"):
            continue
        module = importlib.import_module(f"{__name__}.{name}")     # 自动发现
        tool = getattr(module, "TOOL", None)                        # 唯一契约
        # ……三条硬校验，见第 4 节……
        specs.append(tool)
    return specs


_SPEC_LIST = discover()
SPECS = {s.name: s for s in _SPEC_LIST}                  # name -> ToolSpec
TOOLS = {s.name: s.run for s in _SPEC_LIST}              # name -> 可调用函数（旧 API）
```

`pkgutil.iter_modules(__path__)` 负责列出同目录模块，`importlib.import_module` 负责加载，
模块里的 `TOOL` 即注册凭证。跳过名单只有 `__init__ / base / spec` 与下划线开头的私有模块。

## 4. 三条硬校验（违反直接 raise，不 warn、不静默跳过）

| # | 校验 | 违反时的行为 |
| --- | --- | --- |
| a | `TOOL.name` 必须等于模块文件名（去掉 `.py`） | `ValueError`，消息里带**完整文件路径**、实际 `name` 与期望文件名 |
| b | 工具名不能重复 | `ValueError`，消息里带两个冲突文件路径 |
| c | `description` 与 `parameters` 必须非空 | `ValueError`，分别说明缺哪个、为什么不能缺 |

额外两条"防呆"（同样 raise）：

- 模块没有导出 `TOOL`（而名字又不在跳过名单）→ `ValueError`，提示"补 TOOL 或以 `_` 开头命名"；
- 模块导入本身失败 → `ValueError`，消息形如「工具注册失败：导入 `xxx.py` 时出错：…」，避免只看到一句裸 `ImportError`。

现场"故意搞坏"实测（把 `kg_lookup.py` 的 `TOOL.name` 改成 `kg_lookup_typo`）：

```text
$ python -c "import app.tools"

与文件名 'kg_lookup' 不一致。name 必须等于模块名（去掉 .py），否则无法按名字定位工具。
```

| 名称 | 来源 | 说明 |
| --- | --- | --- |
| `TOOLS` | `tools/__init__.py` 构建 | `dict[str, Callable[..., ToolOutcome]]`，调用方式 `TOOLS[name](ctx, **args)` 不变 |

| `EVIDENCE_CONSTRAINT` | `base.py` 定义、`__init__.py` 再导出 | kb_search 使用 |

新增（不属于旧 API，可放心用）：`SPECS`（name → ToolSpec）、`discover()`、`ToolSpec`。

## 7. 这个改法在本项目上的隐患（重点）

### 7.1 打包/冻结时可能扫不到（最高风险）

`pkgutil.iter_modules(__path__)` 依赖**真实文件系统目录**。用 PyInstaller / zipapp / egg
发布时，工具模块可能打不进包、或在冻结环境里枚举不到，结果是：

- 好的一面：会直接 raise「没有发现任何工具模块」，**不会静默丢工具**；
- 坏的一面：整个服务起不来。

本项目 Dockerfile 目前是"环境 + 源码运行"（`uvicorn app.main:app`），风险低；
若将来要单文件分发，需要给打包器显式 `hiddenimports`，或增加"静态清单兜底"
（`try: discover() except: use(_BUILTIN_SPECS)`）——但那等于又回到维护清单，建议届时改用
`importlib.resources` + 显式清单生成脚本，而不是手写。

### 7.2 启动时全量 import，一个坏工具拖垮全局

`import app.tools` 会 import 所有工具模块。任何一个模块顶层依赖出问题（缺包、语法错、
循环 import），整个后端（包括 `/api/health`）都起不来。本次仅把错误信息补成"带文件名"，
没有做"坏工具隔离"。

- 现有 11 个工具都把重依赖（`app.domain` / `app.geometry` / `app.vision`）放在 **run 内部延迟 import**，
  所以启动只加载轻量模块；
- 新增工具请保持这条约定：**顶层只 import `base/spec` 和标准库**，重依赖放函数里。

### 7.3 循环 import 风险

注册表在包初始化阶段 import 工具模块，工具模块只能 `from .base import ...` / `from .spec import ...`，
**不能 `import app.tools` 包本身**（此时包只初始化到一半），也不能在顶层 import
`app.orchestrator`（后者 `from .tools import TOOLS`，会形成环）。
这一条是隐性契约，建议以后在 `spec.py` 的 docstring 里继续强调（现已写入）。

### 7.4 名字即契约，但路由字符串不会自动跟着改

`TOOL.name == 文件名` 只保证注册正确；`orchestrator._plan()` 里的 `"name": "tolerance_calc"`、
`main.py` 里的 `TOOLS["sketch_grade"]` 仍是**字符串引用**。把工具改名/删掉时：

- `check_tools.py` 会检查 `_plan()` 的引用（本次已纳入），能提前发现；
- 但 **`main.py` 里的 `TOOLS["sketch_grade"]` 还没纳入检查**——这是当前检查的盲区，
  建议下一步把 `check_tools.py` 的引用扫描扩展到 `app/*.py` 全文（本次不动 main.py，故未做）。

### 7.5 注册顺序变了

`pkgutil.iter_modules` 按规定返回排序后的模块名，因此 `TOOLS` / `/api/health.tools` 现在是
**字母序**（改造前是业务手写序）。名字集合完全一致，但如果有前端或脚本依赖旧顺序，需要显式排序。
影响面：`/api/health`、`/api/admin/overview.config.tools`（均为只读展示）。

### 7.6 `TOOL_LABELS` 变成"双轨制"

`orchestrator._tool_label()` 仍读旧的 `TOOL_LABELS` 短标签（为了不改 orchestrator），
而每个 `ToolSpec.label` 是带 `{参数}` 占位符的新文案。后果：

- 新增工具若没登记 `TOOL_LABELS`，事件流里该工具标签会退化成英文 name（功能正常，展示不统一）；
- 两处文案可能漂移。

建议下一次允许改 orchestrator 时，用 `SPECS[name].label` 统一渲染，删除 `TOOL_LABELS`。

### 7.7 参数 schema 只保证"非空"，不保证"和函数签名一致"

`parameters` 是 JSON Schema，写错字段名不会在启动时报错；运行期 `call()` 会用 `**_` 吞掉
未知参数或抛 `TypeError`（被兜成 error outcome）。`check_tools.py` 做了软校验
（对没有 `**kwargs` 的工具检查 properties 是否都在签名内），但仍是弱约束。
建议：给工具写最小调用样例或做 JSON Schema 校验后再上 function calling。

### 7.8 目录内任何 `.py` 都会被加载

动态发现意味着有人往 `tools/` 放一个临时脚本（非下划线、非跳过名单），它就会被当工具加载执行；
没写 `TOOL` 会直接 raise（不会静默），但**代码会被执行**。这是"自动发现"的固有代价，
需靠代码评审 + 目录写权限控制；切忌把临时调试脚本直接扔进 `tools/`。

### 7.9 热重载/进程缓存

uvicorn 未开 `--reload` 时，改工具文件必须重启服务才生效；同一进程内 `importlib` 会缓存模块，
测试里若"改文件再 import"必须在**新进程**里验证（本次故意搞坏测试就是用新进程跑的）。
开发期建议 `uvicorn ... --reload`。

### 7.10 静态扫描脚本的隐性耦合

`check_reachability.py` 原来直接读 `tools/__init__.py` 抓 `artifact_type="..."`；
工具分散后必须改成扫描整个 `tools/*.py`（**本次已同步修改**），否则会误判"后端可产出 0 种"。
以后任何"按单文件扫描源码"的脚本都要检查一遍。

### 7.11 平台大小写

Windows 文件系统大小写不敏感、Linux 敏感。硬校验要求 `TOOL.name` **严格等于**文件名，
所以 `Kb_Search.py` 与 `name="kb_search"` 在两种平台上都会报错，行为一致——这是有意为之。

## 9. 以后怎么新增一个工具

```python
# apps/api/app/tools/my_tool.py  ← 文件名 = 工具名
from .base import ToolContext, ToolOutcome
from .spec import ToolSpec


def my_tool(ctx: ToolContext, foo: str = "", **_) -> ToolOutcome:
    return ToolOutcome(summary=f"foo={foo}", artifact_type="", payload={"foo": foo})


TOOL = ToolSpec(
    name="my_tool",                       # 必须等于文件名
    label="我的工具 · {foo}",
    description="给模型看的说明：什么时候该调用它。",
    parameters={                          # 非空 JSON Schema
        "type": "object",
        "properties": {"foo": {"type": "string", "description": "示例参数"}},
        "required": [],
    },
    run=my_tool,
)
```

三步：

1. 新建文件、导出 `TOOL` → `app.tools` 启动时自动发现，`check_tools.py` 自动纳入；
2. 运行 `python apps/api/tests/check_tools.py` 确认注册；
3. **若希望编排器会选它**，仍需在 `orchestrator._plan()` 里加一条路由规则
   （本次只做注册机制，路由不在范围内；`check_reachability.py` 会把"注册了但编排器从不选"的工具报成 DEAD）。

## 10. 结论

- 11 个工具全部迁入独立模块，函数体零改动，`TOOL` 元数据齐全；
- `TOOLS` / `ToolContext` / `ToolOutcome` / 11 个函数名 / `TOOL_LABELS` / `call` 等公共 API 全部兼容；
- `check_tools.py` 全绿，`verify_all.py` 原有 9 项 + 新增 1 项 = **10/10 全绿**；
- 故意改坏 `TOOL.name` 时导入直接 raise 并指明文件，改回后恢复；
- 主要隐患集中在**打包/冻结**、**启动全量 import**、**名字字符串路由**三处，已在上文给出缓解建议。
