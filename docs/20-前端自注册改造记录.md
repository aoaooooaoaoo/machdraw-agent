## 2. 自注册机制（代码）

### 2.1 `lib/canvasFeature.ts`（新增）

```ts
import type { ComponentType } from 'react';
import type { ArtifactState } from './types';

/** 与历史 CanvasProps 等价，保留 demo 兼容示例数据。 */
export interface FeatureProps {
  artifact: ArtifactState;
  onAsk: (text: string) => void;
  demo?: boolean;
}

export interface CanvasFeature {
  id: string;            // 必须等于 features 下的目录名
  title: string;         // 逐字沿用旧 registry
  hint: string;
  artifactTypes: string[]; // 全局唯一
  order: number;           // 空态列表顺序（旧声明序）
  Component: ComponentType<FeatureProps>;
}
```

### 2.2 `modules/registry.ts`（重写核心）

```ts
const modules = import.meta.glob<{ default: CanvasFeature }>('../features/*/index.ts', {
  eager: true,
});

const features: CanvasFeature[] = [];
for (const [path, mod] of Object.entries(modules)) {
  const dir = path.split('/')[2] ?? '';
  const feature = mod?.default;
  if (!feature) { console.warn(`[registry] ${path} 没有默认导出 CanvasFeature，已跳过`); continue; }
  if (feature.id !== dir) {
    console.warn(`[registry] feature.id "${feature.id}" 与目录名 "${dir}" 不一致，已跳过 ${path}`);
    continue;
  }
  if (!Array.isArray(feature.artifactTypes) || feature.artifactTypes.length === 0) {
    console.warn(`[registry] feature "${feature.id}" 没有声明 artifactTypes，已跳过`);
    continue;
  }
  features.push(feature);
}
features.sort((a, b) => a.order - b.order);

const REGISTRY: Record<string, CanvasDef> = {};
for (const feature of features) {
  const def: CanvasDef = { title: feature.title, hint: feature.hint, component: feature.Component };
  for (const artifactType of feature.artifactTypes) {
    const previous = REGISTRY[artifactType];
    if (previous) {
      console.warn(
        `[registry] artifactType "${artifactType}" 被多个 feature 注册` +
          `（"${previous.title}" 与 "${feature.id}"），后注册的覆盖前者`,
      );
    }
    REGISTRY[artifactType] = def;
  }
}
```

关键点：

- `import.meta.glob` 是 **Vite 编译期静态展开**（`eager:true`），生产构建会真正打包进 bundle；
  新增 `features/<id>/index.ts` 后**不需要改 registry**。
- `id` 必须等于目录名：不匹配只 warn + 跳过（不阻塞构建，但模块会消失）；
- `artifactTypes` 重复：warn + **后注册覆盖**，与参考作品 `registry.ts` 行为一致；
- 排序用 `order`，保证 `KNOWN_CANVAS_TYPES` 顺序与旧声明一致；`order` 相同时按 glob 字典序
  （约定 order 唯一，见 §6）；
- 三个旧导出保持原样：

```ts
export function getCanvasDef(artifactType: string): CanvasDef {
  return REGISTRY[artifactType] ?? {
    title: `${artifactType} 画布`,
    hint: '该 artifactType 尚未在注册表中登记',
    component: PlaceholderCanvas,
  };
}
export const KNOWN_CANVAS_TYPES = Object.keys(REGISTRY);
export function isPlaceholder(artifactType: string): boolean {
  const def = REGISTRY[artifactType];
  return !def || def.component === PlaceholderCanvas;
}
```

- 新增：`hasCanvasOwner(type): boolean`（供 store 兜底）。
- 新增：`CANVAS_FEATURES`（只读列表，排查注册问题用）。
- `CanvasProps = FeatureProps` 继续从 registry 导出，**9 个 Canvas.tsx 的 import 不用改**。

### 3.1 store 收到 artifact 时

`apps/web/src/lib/store.ts` 的 `applyEvent`：

```ts
case 'artifact': {
  if (ev.artifactType) {
    // ★ 没人认领的 artifactType 不挂画布，也不静默丢弃 ——

```

消息末尾追加：

```ts
const messages = [...session.messages];
messages[idx] = msg;
messages.push(...notices);
```

提示文案：

```ts
function unknownArtifactNotice(types: string[]): ChatMessage {
  const list = types.map((t) => `\`${t}\``).join('、');
  return makeNotice(
    `> ⚠️ **系统提示**：该产物类型暂无画布（${list}），已跳过画布展示。\n>\n` +
      '> 请检查后端工具的 `artifact_type` 是否写错，或前端是否缺少 `features/<id>/index.ts` 注册。',
  );
}
```

`makeNotice` 用 `role: 'system'`（本轮在 `lib/types.ts` 给 `ChatMessage.role` 加了 `system`），
所以：
- 中栏 `MessageItem` 的 `role === 'user' ? ... : assistant` 分支会把它渲染成助手气泡；
- `store.send()` 的 history 过滤 `role === 'user' || role === 'assistant'` 会**自动排除**它，
  不会把系统提示发给模型。

### 3.2 历史/内存恢复时

```ts
function restoreKnownArtifacts(session: SessionState): SessionState {
  const unknown = Array.from(
    new Set(session.artifacts.filter((a) => !hasCanvasOwner(a.artifactType)).map((a) => a.artifactType)),
  );
  if (unknown.length === 0) return session;
  return {
    ...session,
    artifacts: session.artifacts.filter((a) => hasCanvasOwner(a.artifactType)),
    messages: [...session.messages, unknownArtifactNotice(unknown)],
  };
}
```

在 `setActiveFeature(id)` 切模块时调用：把内存会话里已经没人认领的画布过滤掉并补提示。
（当前前端会话**还没有 localStorage 持久化**；这个 guard 是给「未来持久化 + 内存恢复」用的，
见 §6 第 6 条。）

## 5. `check_reachability.py` 改了什么

原脚本用正则扫 `registry.ts` 的 `^  key: {` 来数画布，自注册后 map 是运行时生成的，必须改。

改动（`apps/api/tests/check_reachability.py`）：

1. 顶部加 `import re`（原来是在函数中间 import）。
2. `[2]` 段不再读 `modules/registry.ts`，改为扫 `apps/web/src/features/*/index.ts`：
   - 每个文件校验 `id` 是否存在、是否等于目录名；
   - 用 `artifactTypes\s*:\s*\[([^\]]*)\]` 抽数组里的字符串；
   - 记录 `owners`，发现同一类型被两个 feature 注册 → failure（`registry` 是 warn，这里升级为 failure）。
3. `[3]` 段 `reg_keys` 来自 `registered`（排序后），不再从 registry 文本抽 key。
4. 输出增加「前端 features 注册 N 个 feature / M 个 artifactType」，便于对账。

为什么不能只把 `registry.ts` 的 map 保留成常量：那就退回了硬编码，新增模块仍要改公共文件。

## 6. 水土不服的地方（重点，决定下一阶段要不要继续搬）

### 6.1 “零公共文件”只对**前端画布**成立，后端仍要注册

参考作品的模块是「前端 index 自注册 + 后端工具目录扫描」双端自注册；我们目前只做了前端：

- 新增一个**能对话产出画布**的模块，仍要改后端：
  - `apps/api/app/tools/__init__.py` 的 `TOOLS` 注册；
  - `apps/api/app/orchestrator.py` 的 `_plan()`（关键词/分支）或 `_RETIRED` 移除；
  - `apps/api/app/modules.py`（如果还要在左栏出现）。
- 本次验收的 9 个画布本来就有后端工具，所以“只写 index.ts + Canvas.tsx”成立；
  真正新增第 10 个模块时，前端侧零改公共文件，但后端侧不是。

→ 若要真正做到“新增模块只动一个目录”，下一步需要后端也改成 `pkgutil` 扫描工具目录
（参考作品的 `backend/app/tools/` 就是按目录自动发现）。

### 6.2 数据在后端 vs 参考作品数据在前端

参考作品 `module1` 的 `graphData.ts` 是前端静态数据，artifact 只带 `{mode, focus}`；
我们的 9 个画布都是「后端 artifact.data 下发完整数据」。这带来：

- `CanvasFeature` 里没有 `preview` 的天然位置（参考作品 `preview` 是模块自带样例数据）。
  我们目前仍靠 `CanvasPanel.demoItems(feature)` 的壳内硬编码示例——**新增画布想有演示数据，
  还得改壳**，这正好破坏了“零公共文件”的目标。
- 建议下一阶段把 `preview`/demo 也搬进 `CanvasFeature`（可选字段），并让 `CanvasPanel` 从
  registry 取；这样新模块的示例数据也自包含。
- `autoOpenCanvas` 同理：参考作品是 feature 字段；我们目前是壳里的推断（按模块 id/画布类型），
  新增模块自动展开的规则还得改壳。

### 6.3 前端 bundle 会随模块线性增长

`eager: true` 会把 9 个画布（含 three/graph 的大 SVG 逻辑）全部打进主 chunk。
本次 `index-DIgyyMCE.js` 395.53 kB（gzip 123.43 kB），仍可接受；
但如果新增 10+ 个重画布，应该改成 `lazy`/动态 import（参考作品用 eager 是因为只有 6 个模块）。
注意：改成 lazy 会改变 `getCanvasDef` 的同步签名（Component 需要 Suspense 包装），
不属于本次“零行为变化”范围。

### 6.4 `id`/`artifactTypes` 写错时构建不报错，只在运行时 warn

`registry.ts` 对 `id !== 目录名`、缺 `artifactTypes` 是 warn + skip；
如果没人注意 console，会出现“模块怎么没了”。`check_reachability.py` 现在会校验 id/重名，
但它是**独立脚本**，不在 `npm run build` 里。建议后续把这段校验放进 CI/`verify_all.py`
（`verify_all` 已经跑 reachability，所以实际上已经覆盖；只是本地 `npm run build` 不会拦）。

### 6.5 一个 feature 认领多个 artifactType 时，空态计数语义会变

`KNOWN_CANVAS_TYPES` 是 artifactType 列表，不是 feature 列表：
如果一个模块声明 `['a','b']`，空态会显示“已实现渲染器 10 / 10”，但其实只有 9 个组件。
当前 9 个 feature 都是 1:1，没触发；若以后多对一，需要把空态文案改成“N 个画布类型 / M 个模块”。

### 6.6 “本地恢复历史”目前是空路径

我们的会话只存在内存（`store.ts` 没有 localStorage 持久化），所以 `restoreKnownArtifacts`
实际只会在“热更新/内存里已有旧 artifact”时触发；真正刷新页面会丢会话，不会遇到旧类型。
我仍然实现了它，是为了给“以后加持久化”留一个安全阀；
验收第 4 条的“对话提示”走的是 `applyEvent` 的实时路径，已实测。

### 6.7 组件反向依赖 registry 的类型，形成 type-only 环

9 个 `Canvas.tsx` 仍 `import type { CanvasProps } from '../registry'`；
registry 现在 eager import 各 feature，feature import 各 Canvas。**运行时没有环**
（`CanvasProps` 是 type-only，编译后擦除），但如果哪天某个 Canvas 从 registry 里
import 一个**值**（比如常量），就会形成运行时循环，可能出现 `undefined`。
约定：Canvas 只从 registry 取类型；值一律放 `lib/`。

### 6.8 `order` 并列靠 glob 字典序，属于隐式行为

参考作品也 `sort((a,b)=>a.order-b.order)`，并列时依赖对象插入顺序。
我们约定 order 唯一（10/20/…/90），并在文档里写死；新增模块请继续用 10 的倍数，别复用。

### 6.9 兜底行为是“有意的行为变化”

改造前未知 artifactType 会落到 `PlaceholderCanvas`（显示 JSON 摘要 + “开发中”）；
改造后 store 直接不挂画布 + 对话提示。按本次需求这是**期望的**；
但如果外部客户端/旧历史里仍有未知类型，右栏会少一个占位画布。
`getCanvasDef` 仍保留 Placeholder 兜底，所以直接调用者不受影响。
